---
title: Accounts
description: Snapshot native provider logins so several can coexist and any client can use them.
---

An account is either a login that a provider's own CLI created or a provider key
you supplied for its local proxy. AnyPick snapshots it, so you can keep several,
switch between them, and lend one to a client that was never designed to use it.

## Supported providers

| Provider | Live auth | How other clients reach it |
| --- | --- | --- |
| `claude` | Claude Code Keychain / `~/.claude/.credentials.json` | direct, for Claude Code only |
| `codex` | `~/.codex/auth.json` | direct, for Codex only |
| `grok` | `~/.grok/auth.json` | built-in dual proxy (OpenAI + Anthropic) |
| `opencode` | OpenCode auth store | built-in Zen/Go dual proxy |
| `gemini` | `~/.gemini/` (`.env`, oauth, accounts), Antigravity state/keyring | built-in dual proxy → Gemini API |
| `kiro` | kiro-cli secret store, `~/.aws/sso/cache`, or an API key you supply | external `kirolink` / `kiro-proxy`, if installed |
| `workbuddy` | WorkBuddy / CodeBuddy subscription (device-flow OAuth) | built-in OpenAI proxy, serving the clients above; `anypick use workbuddy/<name>` also switches the WorkBuddy app itself via its session file |
| `cline` | ClinePass / Cline WorkOS login | built-in OpenAI proxy (no Cline client adapter yet) |

`anypick providers` is the authoritative inventory for the build on your
machine. In addition to the native providers above, the Go engine ships the
compatible API-key and subscription-key providers directly; they do not
require a `popular-providers` plugin. See
[Compatible providers are built in](/docs/guides/plugins#compatible-providers-are-built-in)
for the credential profiles and examples.

<Aside type="caution" title="Account backups contain credentials">
Account backup files are readable JSON and are not encrypted by AnyPick. Store
them like working credentials. They cover saved accounts; gateway secrets,
preferences, and activity history are not a complete application backup.
</Aside>

## Saving a login

AnyPick delegates browser sign-in to provider-owned login launchers and then
reads the credential they write to the provider's normal location. Two ways in:

<Tabs>
<TabItem label="Save the live login">
```bash
claude login
anypick add account claude --current --name personal

codex login
anypick add account codex --current --name personal
```
The credential that is live right now becomes a saved snapshot named
`codex/personal`.
</TabItem>
<TabItem label="Start a fresh login">
```bash
anypick add account codex --new --name work
```
When an installed provider exposes browser Auth, AnyPick backs up the live
credential, opens the provider's browser flow, verifies the new native login,
and saves it under the new name in one command. Codex, Claude Code, Kiro, Grok,
and Gemini provide this path. Z.ai also supports importing the encrypted ZCode
login on this Mac or starting its official browser flow. Gemini's picker has separate Gemini CLI and
Antigravity-compatible Google sources; AnyPick opens the Google OAuth flow
directly because `gemini` itself has no login-only command. If no browser
launcher is available, AnyPick falls back to clearing the live login and tells
you how to save it after signing in with a provider-supported tool.
</TabItem>
</Tabs>

Official methods are shown first and are the default because they are less
likely to conflict with provider policy. They are not a whitelist: a full
provider plugin may expose a community method, and you can choose it explicitly
with `--auth-method <id>` or the method picker. Provider terms still apply.

A login is saved once. Saving credential material AnyPick already holds under a
second name is refused and the error names the account that already has it:
use that account, or remove it
(`anypick account remove <provider>/<name>`) before saving under a new name.
Two names for one snapshot would otherwise look like two accounts that
switched nothing; `anypick doctor` reports the pairs saved before this rule.

If browser sign-in or snapshot saving fails, AnyPick restores the previous
native login and active-account pointer. Authorization URLs, one-time codes, and
launcher output are not copied into tray or JSON output.

For Gemini, `--source gemini-cli|antigravity` picks which sign-in to read when
both exist. In the macOS app, **On This Mac** imports the subscription already
logged in to Gemini CLI or Antigravity. **New Account** lets you choose either
Google source and sign in as another account. A failed or cancelled flow
restores the previous login and active account; AnyPick never writes a new
login into Antigravity's IDE database or keychain.

Gemini API keys (`GEMINI_API_KEY` or `GOOGLE_API_KEY`) can also be saved as
named native accounts. This is separate from a gateway profile and works even
when no Gemini CLI or Antigravity login is present:

```bash
anypick add account gemini --credential api-key --secret --name studio
```

The macOS Add Login sheet keeps all three Gemini paths available: the login
already on this Mac, a new Google subscription login, and a separate API-key
form. The API-key path is AnyPick-owned and does not replace the native login.

## Saving a key instead of a login

Some providers accept a key you already hold. The generic form is:

```bash
anypick add account mimo --credential subscription-key --secret --name work \
  --option profile=singapore
```

Omit the `--secret` value and AnyPick prompts for it on a terminal, so the key
never enters your shell history. Every `--option key=value` must be a qualifier
declared by that provider (`profile` today). The CLI fails closed on anything
else instead of silently dropping it.

> **Kiro API keys are not accepted yet.** The `kiro` provider declares no
> `CredentialDefinitions` (it is not a `CredentialInputProvider`), so
> `add account kiro --api-key/--region` fails closed in `SaveInput` with
> `UNSUPPORTED_CREDENTIAL_INPUT`, and a bare `--region` is refused in
> `cmd/anypick/main.go` before it reaches the provider. Kiro logins via
> browser sign-in (`--new`) and snapshots of the live login (`--current`)
> work as documented.

In the [terminal UI](/docs/guides/terminal-ui) the same flow is
**Use an API key instead** on the add-account screen, offered for providers
that declare typed credential products. The key is hidden as you type it, and
endpoint profiles render from the provider contract.

A key is not a login on this machine: it is stored only in AnyPick, so
activating it leaves any native login on disk untouched, and
`account refresh` will not overwrite it.

Providers installed by a plugin can declare other credential products without
adding provider-specific CLI flags. The generic form is:

```bash
anypick add account <provider> --credential <kind> --secret --name <name>
anypick add account mimo --credential subscription-key --secret --name work \
  --option profile=singapore
```

Every `--option key=value` must be a qualifier declared by that provider. The
TUI renders the same kinds and endpoint profiles from the provider contract.
In the macOS app, these providers show an API-key form in Add Login instead
of a sign-in flow.

### Local model servers

Ollama and LM Studio serve models from your own machine, so they need no key.
Save the server as an account:

```bash
anypick add account ollama --credential server --name local
anypick add account lmstudio --credential server --name local
```

That points at the default address on this computer:
`http://127.0.0.1:11434/v1` for Ollama and `http://127.0.0.1:1234/v1` for LM
Studio. For a server elsewhere, pass its URL as the profile:

```bash
anypick add account ollama --credential server --name lan \
  --option profile=http://192.168.1.20:11434
```

A URL without a path gets `/v1`. If you turned on LM Studio's API key, add
`--secret`. AnyPick sends a key only over HTTPS or to a server on this
computer, so a key for a plain-HTTP server elsewhere on the network is refused.

Claude Code, Codex, pi and omp use the account through AnyPick's proxy, which
translates Claude Code's requests to the server's OpenAI-compatible API. In the
apps, these providers show the key field as optional in Add Login.

<Aside type="caution" title="One live login at a time">
Provider CLIs normally keep one credential in their default home. Saved
accounts live in AnyPick's store, and ordinary activation restores the selected
one into that provider path. Codex named profiles are the exception: each one
gets an isolated `CODEX_HOME`, so multiple Codex CLI accounts can run at once.
Do not edit a managed auth file by hand while its profile is active.
</Aside>

## Using an account

```bash
anypick use codex --with codex/personal    # same-protocol: direct
anypick use claude --with grok/work        # cross-protocol: proxy starts on demand
anypick use commandcode --with workbuddy/work --model deepseek-4.1-flash
anypick run commandcode --with workbuddy/work --model deepseek-4.1-flash --
anypick run claude
```

Codex CLI also supports named routes. AnyPick gives each named route its own
`CODEX_HOME`, native profile config, and `auth.json`, so profiles can point at
different saved accounts or gateways without overwriting the global Codex
config or login:

```bash
anypick codex profile login personal
anypick codex profile login work
anypick use codex --with codex/personal --profile personal
anypick use codex --with codex/work --profile work
anypick use codex --with hub:default --profile shared
anypick codex profile list
anypick run codex --profile work -- exec --help
```

`profile login` opens the official Codex sign-in in the selected profile home,
then saves the resulting credential as `codex/<name>` and materializes the
profile. It does not replace the desktop app's default `~/.codex/auth.json`.
For an account already saved in AnyPick, `anypick use ... --profile <name>`
copies its snapshot into the profile home. Gateway-backed profiles use their
saved endpoint directly. If a profile should use an account-specific AnyPick
proxy instead of native Codex auth, enable the account proxy and pass
`--transport proxy`. A Hub-backed profile has a separate route token, so it
does not invalidate another Codex profile. The default Codex CLI config can
also use an account proxy or Hub directly:

```bash
anypick use codex --with codex/work --transport proxy
anypick use codex --with hub:default
```

These routes configure Codex CLI. Codex Desktop opened from the Dock retains
its own signed-in account. To use a profile in the desktop app, run
`anypick codex profile open <name>` (macOS) or choose **Open in Codex App** from
the profile's actions menu: it opens a separate Codex window on that profile.

When the client and the account speak different protocols, AnyPick starts a
local translating proxy and points the client at it. You do not start the proxy
yourself — Command Code receives an OpenAI-compatible `anypick-managed` provider
in `~/.commandcode/providers.json`; its per-instance proxy token is kept in
`~/.commandcode/auth.json`. See [Proxies](/docs/guides/proxies) if you want to.

## Live usage and quota

When a provider reports live usage, the macOS app shows it in the account and
app details. Antigravity reports weekly and five-hour windows grouped by model
family, such as **Gemini Models** and **Claude and GPT models**. AnyPick reads
the current provider credential for this display; it does not refresh or write
the login. Usage is available only when the provider account is active on this
Mac. Codex Desktop keeps its own sign-in separate from Codex CLI, so AnyPick
does not show a quota reading when those accounts do not match.

## Managing saved accounts

```bash
anypick account list                   # or: anypick list accounts
anypick account refresh codex          # refresh the live login
anypick account refresh codex work     # refresh one saved account
anypick account refresh codex --all    # refresh every saved account
anypick account remove codex old -y
```

`refresh` renews OAuth tokens in place. The account keeps its name, so bindings
that point at it keep working; nothing needs re-binding. It exits non-zero if any
target failed, and prints which one.

`remove` also removes every named Codex profile whose route was that account
(see [Named Codex profiles](/docs/reference/cli#named-codex-profiles)). A
profile owns a private `CODEX_HOME` holding the account's `auth.json`, so
leaving it behind would strand a credential nothing in AnyPick could reach
again. The cleanup is reported, not silent:

```bash
anypick account remove codex work -y
# removed codex/work Removed named profile(s): codex/work.
```

Profiles that point somewhere else — a gateway, a Hub, a pool, or another
saved account — are left alone. Deleting one account never takes down a profile
that uses a different source. If the account row is already gone but a profile
still points at it (a delete from an older AnyPick, a crash between the two
writes, or a database restored without its account rows), AnyPick removes the
profile the next time it starts and says so on stderr; `anypick doctor` reports
it before that.

## Export and import

Move an account to another machine:

```bash
anypick account export codex work -o ./work.json
anypick account import codex work -i ./work.json
```

When `--out` is omitted, export writes an owner-only `.json` file under
`~/.anypick/exports/` and prints its exact path. To move several accounts in
one package, export all accounts (or one provider) to a single JSON backup:

```bash
anypick account export --all --out ./accounts.json
anypick account import ./accounts.json
```

You can also import several single-account JSON files in one command, for
example `anypick account import ./work.json ./personal.json`. `import` refuses
to overwrite an existing name unless you pass `--force`. A login identity
already saved under a different name remains blocked, including with `--force`;
use that existing name when replacing it. API key display labels do not count
as login identities.

CLI, TUI, and desktop imports accept both single-account exports and account
backups. The desktop file picker accepts `.json` and `.anypick-backup` files,
and lets you review the accounts before importing.

<Aside type="danger" title="Exports contain live credentials">
An exported file holds the real tokens in plain form. Treat it like the
credential it is: transfer it over a channel you trust and delete it afterwards.
</Aside>

## Model defaults

When a binding attaches an account proxy to Claude, AnyPick sets the Claude
model roles:

- `ANTHROPIC_MODEL` — the default
- `ANTHROPIC_DEFAULT_SONNET_MODEL`, `…_OPUS_MODEL`, `…_HAIKU_MODEL`

The values come from the running proxy's live `/v1/models` catalog when one is
available, so newly released models appear without a AnyPick update. Change them
later with <kbd>m</kbd> on the Proxy or Gateways board, from Apps by rebuilding
the route, or by re-binding with an explicit `--model`.
